How shaledb works

Each database has one writer and many readers. shaledb stores immutable SSTs in R2 and versions each database's manifest with compare-and-swap, or CAS. The writer is a Durable Object whose SQLite table is both the write-ahead log and the memtable. A Cloudflare Workflow runs compaction. Click the diagrams to step through them.

    04

    Write path and flush

    A write is durable once SQLite commits it. A flush uploads the unflushed rows as one L0 SST and commits a new manifest by CAS. Only then does the writer mark the rows flushed. The rows stay in SQLite for transactions until a trim removes them.

    Read path

    Reads run in the API Worker's isolate, not in the writer. The consistency level decides whether a read calls the writer. Block bytes come from two caches in front of R2.

        07

        Compaction

        The compactor plans jobs, and a Workflow runs them. The compactor records each job in its state before it launches the job. A job's commit replaces exactly its inputs and records its job id, so a retried commit changes nothing.

        08

        Garbage collection and the maintenance sweep

        Each database's compactor runs that database's garbage collection, one collection at a time. The cron sweep handles the cases that no compactor handles: removed databases, lost wakes, and holds that forks keep on their sources.

            09

            Database lifecycle and sharding

            Every lifecycle change is a manifest CAS. A fork copies no data. It references the source's SSTs and holds the source until the fork's compactions have rewritten them.
