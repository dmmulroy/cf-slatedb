shaledb: SlateDB's LSM, rebuilt on R2 and Durable Objects

A design sketch, not an implementation. It keeps SlateDB's model: one writer, many readers, immutable SSTs, a CAS-versioned manifest, and size-tiered compaction. It swaps two pieces for Cloudflare-native ones. The writer is a Durable Object whose SQLite storage is both the WAL and the memtable. Compaction runs in a Workflow. Code follows iac/docs/coding-standards.md and was checked against the installed effect@4.1.4 and @alchemy.run/cloudflare@2.0.0-beta.87.

1. What changes from SlateDB

3. Write path: the WAL is the memtable's SQLite table

There is one write path. The writer Durable Object's SQLite table memtable_rows is both the WAL and the memtable. There's no WalStore abstraction and no R2 WAL. Optional changelog export at each flush provides change data capture.

put(key, value)

  1. WorkerDbClient.put → POST /v1/databases/:id/batches to WriterServer
  2. Durable ObjectSemaphore(1): seq = oracle.next; INSERT rows + meta in one storage.transaction
  3. Durable ObjectThe response waits until SQLite is durable, so the acknowledgement means the write is durable
  4. Durable ObjectIf memtable bytes exceed l0SstSize, or maxL0Age has passed: setAlarm(now)
  5. Durable Objectalarm: stream rows in (key, seq desc) order → SstBuilder
  6. R2PUT compacted/<ulid>.sst (and the changelog, if enabled), then CAS manifest/<n+1> with an epoch check
  7. Durable ObjectDELETE rows WHERE seq ≤ lastL0Seq

Consequences

Why not SlateDB's R2 WAL

  • It has no good home for the memtable. Effect 4 has no sorted map, and a Durable Object can be evicted at any time. An in-memory skiplist would need to be written and then rebuilt from R2 on every wake-up. A SQLite memtable would mean writing every row twice with no durability gain.
  • It's worse at the main job. Either it loses up to one flushInterval of acknowledged writes, or acknowledgements wait for a PUT plus the interval (about 100 ms or more).
  • It costs more: up to 10 Class A PUTs per second per active database at a 100 ms interval.
  • It's more to build and test: fencing by WAL file id, WAL replay, awaitDurable waiters, and a second test layer.
  • Its one real advantage, CDC, doesn't need it. See the changelog export.

The real risk of this choice: until the next flush, durability is Durable Object storage's (replicated by Cloudflare before the acknowledgement), not R2's. maxL0Age bounds how long that lasts.

4. Read path

get(key, { consistency })
  manifest = ManifestCache.current   # Resource, refreshed on a schedule
  match consistency
    Flushed        → no writer call
    AtLeast(seq)   → if manifest.lastL0Seq ≥ seq, no writer call   # seq from a WriteReceipt
                     else treat as Latest
    Latest         → WriterServer.probe(key)   # one SQLite index lookup, no SST I/O
                       returns { row: Option, flushedSeq }
                     if row is some → return resolve(row)
                     if manifest.lastL0Seq < flushedSeq → refresh manifest
                     # writer deletes rows only after the manifest commit,
                     # so memtable ∪ manifest(≥ flushedSeq) covers every write
  # all SST work runs in the caller's isolate, never in the writer
  for sst in manifest.l0 (newest first), then each sorted run
    if not sst.range.contains(key) → skip
    if bloom(sst).definitelyNot(key) → skip
    block = BlockCache.get(sst.id, indexSearch(key))
    row   = block.seek(key, snapshotSeq)
    if row → return resolve(row)
  return Option.none()

Cache tiers (SSTs are immutable, so no invalidation)

  • Isolate memory: an Effect Cache keyed by sstId:blockIndex, with metadata in a separate cache so scans don't evict indexes and filters (SlateDB's SplitCache). It holds plain Uint8Arrays and no I/O objects, so it can outlive an invocation.
  • L2, Workers Cache in front of BlockServer: a cache in the nearest data center, then an upper tier shared by the whole network. A hit doesn't run the Worker. Concurrent misses for one key collapse into one run. This replaces the old caches.default Cache API, which has no tiering or collapsing, still runs the Worker, and needs explicit put(). It plays the role of SlateDB's Foyer disk tier.
  • R2: get(key, { range }), called only by BlockServer on an L2 miss. R2 has no egress fees, but every GET is a Class B op.

A Flushed read never calls the writer, so a stale manifest only makes it older, never wrong. Latest costs the writer one cheap request. The writer's ~1k req/s budget therefore goes to writes, and reads scale out across isolates (§12).

Block addressing for Workers Cache

Cache-Tag: db:<db>

Rules

  • A separate Worker, cache on Worker-wide. Alchemy supports per-entrypoint cache settings (WorkerProps.entrypoints), but named entrypoints are plain async WorkerEntrypoint classes. A separate Effect-native BlockServer keeps one handler style.
  • Cloudflare.cache({ crossVersionCache: true }), because the served bytes are raw SST bytes that don't depend on the deploy. Otherwise every deploy would empty the block cache.
  • The owning database is in the path, not ctx.props. Alchemy drops props on service bindings at upload, and binding props are fixed at deploy time anyway. Database id plus ULID makes each path unique by construction.
  • Reachable only through the service binding: no custom domain, workersDev: false. Callers authorize access to the database before they fetch.
  • fetch(), never RPC. Custom RPC methods bypass Workers Cache.
  • Each SstHandle carries metaOffset and metaLength, so opening an SST is one cacheable request, not a suffix probe.
  • The response-size cap at launch is the Free-plan 512 MB. Blocks are KBs.

Neither Vitest nor alchemy dev emulates Workers Cache. blockSourceTestLayer reads the in-memory object store. Verify hits on a deployed preview with Cf-Cache-Status: HIT.

5. Manifest CAS and fencing

WriterServer init (blockConcurrencyWhile)
  loop
    latest = ManifestStore.loadLatest()        # GET manifest/LATEST hint, then
                                               # HEAD id+1 … until 404 (no R2 LIST)
    next   = latest with writerEpoch + 1
    ManifestStore.create(latest.id + 1, next)  # If-None-Match: *
      ManifestConflict → retry with backoff
  store writerEpoch in SQLite meta

flushL0
  rows = SELECT … WHERE seq <= cut ORDER BY key, seq DESC
  sst  = SstBuilder.build(rows)               # ULID name
  SstStore.put(sst)                           # orphan if we lose
  ManifestStore.update(m =>
    m.writerEpoch != ours → fail WriterFenced
    m with l0 = [sst, ...m.l0], lastL0Seq = cut)
  ObjectStore.put(manifest/LATEST, newId)     # best-effort hint
  DELETE FROM memtable_rows WHERE seq <= cut

Invariants

  • A manifest id is created exactly once. Losing the race means reloading and reapplying a pure (Manifest) => Manifest edit.
  • SST names are ULIDs, so a fenced writer can only leave orphans. GC removes them after minAge.
  • The compactor applies the same rule with compactorEpoch. A job's edit replaces exactly its input ids. If they have changed, the edit fails rather than merging.
  • Rows are deleted from SQLite only after the manifest commit, so a crash in between replays as duplicate rows with identical seqs, which merging deduplicates.
  • manifest/LATEST is only a hint and may be behind. Probing id+1 finds the real head. Create-if-absent ids still decide, and R2 LIST (a Class A op) never runs on a read path.

To verify: the R2 binding onlyIf object form once treated * as a literal etag (workerd #2572). Pass new Headers({ "If-None-Match": "*" }) and cover it with an integration test against real R2.

8. Public API and semantics

interface IDbClient {
  put(db, key, value, opts?)    → Effect<WriteReceipt, DbWriteError>
  delete(db, key)               → Effect<WriteReceipt, DbWriteError>
  merge(db, key, operand)       → Effect<WriteReceipt, DbWriteError>
  write(db, WriteBatch)         → Effect<WriteReceipt, DbWriteError>
  get(db, key, { consistency })  → Effect<Option<Uint8Array>, DbReadError>
  getRow(db, key, …)            → Effect<Option<Row>, DbReadError>  // seq, timestamps
  scan(db, range, …)            → Stream<Row, DbReadError>
  flush(db)                     → Effect<void, DbWriteError>
}
type ReadConsistency =
  | { _tag: "Latest" }                // SlateDB Memory: one writer probe
  | { _tag: "AtLeast"; seq: SeqNum }  // read-your-writes from a receipt
  | { _tag: "Flushed" }               // SlateDB Remote: no writer call
// WriteReceipt = { seq: SeqNum, createTs: Timestamp }   // durable on return; no awaitDurable
  • Durability: a write is durable once the call returns, because DO SQLite has confirmed it. SlateDB acknowledges from memory.
  • Atomicity: a WriteBatch commits as one SQLite transaction with one seq.
  • Ordering: seq decides visibility. Wall-clock time is only metadata, from a monotonic clock seeded by lastL0ClockTick.
  • Latest reads see every acknowledged write and cost the writer one memtable probe. AtLeast(seq) sees the caller's own writes and usually skips the writer. Flushed reads see L0 and below, up to one memtable behind, and never touch the writer.
  • Scope of atomicity: batches and transactions are atomic within one database. If a caller splits data across databases (for example with the sharding package), keys that must change together need to stay in the same database.
  • Lifecycle errors: KeyOutOfRangeError (not retryable; the key is outside the database's keyRange) and DatabaseSealedError { successors } (not retryable against this database; route to a successor).
  • Errors follow docs/errors.md: WriterFencedError (not retryable), WriteStalledError (retryable, compaction is behind), ManifestConflictError (internal and retried), SstCorruptedError (checksum, not retryable), ObjectStoreUnavailableError.
  • Later versions: optimistic transactions, which are cheap here because the conflict check is a SQLite lookup on the writer. Also checkpoints, clones, merge operators, and TTL during compaction.

Gaps to build privately (Effect doesn't provide these)

  • sorted map v4 has no SortedMap or RedBlackTree. Use DO SQLite. BLOB comparison is memcmp, which matches Bytes.Order.
  • k-way merge Stream has merge/mergeAll but not mergeSorted. Build a private binary heap over Pull sources, ordered by (key asc, seq desc). TxPriorityQueue is transactional and too heavy for this.
  • checksums crypto/Digest covers MD5 and the SHA family only. Write a private CRC32C table, about 30 lines.
  • bloom filter private, double hashing over a single 64-bit hash, sized by filterBitsPerKey.
  • ulid private: Clock plus Random. cluster/Snowflake also sorts by time but ties ids to machine ids.
  • compression Workers' built-in CompressionStream handles gzip and deflate. I'm not certain about zstd or lz4 (they may need WASM), so check before relying on them. Start uncompressed.

11. Trade-offs and open decisions

  • The SQLite WAL is limited to one location. One DO holds at most 10 GB, so maxUnflushedBytes (about 256 MB) applies backpressure long before that limit. Writes always go to one placement, so distant callers pay a round trip.
  • One writer per database. One logical dataset can grow past a single writer by spreading it over range-bounded databases (§12). A single hot key is still capped at one Durable Object; the storage layer can't fix that.
  • Binary over the HTTP boundary. The standards require Effect HttpApi rather than Alchemy RPC. Base64 JSON (Uint8ArrayFromBase64) costs about 33% extra. An application/octet-stream batch body would avoid that. Decide before v1 routes are fixed.
  • Memory limit. Isolates get 128 MB, so compaction must stream blocks in and stream multipart parts (at least 5 MiB) out. Input SSTs are never fully buffered.
  • Cost model. Each memtable flush costs one PUT plus one manifest PUT. Each compaction output costs about one PUT per 5 MiB part. Every DO SQLite row written is billed. Use a 64 MB L0 size to amortize.
  • Wait to decide: JSON vs SchemaBinary manifest, the default changelogRetention, and whether readers should use checkpoints (as SlateDB does) or a GC minAge margin.

12. Multi-tenancy: core primitives, optional sharding

The core has no tenant concept. Its unit is a database: one opaque DatabaseId with its own WriterServer, CompactorServer, manifest chain, R2 prefix, and cache tag. Tenancy is a mapping from tenant to databases, which callers own. SlateDB takes the same position. The core adds only the primitives a layer can't build safely: range bounds, seal, zero-copy range fork, and GC that respects forks.

How callers scale without built-in tenancy

1 · One database per tenant (default)DatabaseId.make(`tenant-${id}`). Routing is a pure function of the id, with no directory. Isolation, deletion, and residency are per database. Idle cost is about zero: the DO hibernates, and small data stays in SQLite until maxL0Age flushes it.
2 · Pooled key prefixes (rarely right)Many tiny tenants in one database under tenantId/ keys. They share one writer's ~1k req/s and backpressure, deleting one is a range delete plus compaction, and there's no per-tenant residency. Option 1 is already cheap at scale.
3 · Datasets beyond one writerUse the optional @shaledb/sharding package, or the same core primitives from your own code. Range-bounded databases split by forking without copying data.

  ManifestStore.update(m => m with state = Sealed(successors),
                                   writerEpoch + 1)   # fences writer
  later writes → DatabaseSealedError { successors }

DatabaseLifecycle.remove(id)
  forks still hold checkpoints → DatabaseHasDependentsError
  else: clear DO storage · remove db/<id>/ · purge tag db:<id>

Why GC stays per database

  • This reuses SlateDB's clone mechanism. A fork holds a checkpoint in its source's manifest, so the source's GC, reading only its own manifests and checkpoints, keeps every SST the fork still reads.
  • GC never scans other databases. A fork releases its checkpoint once compaction has replaced every external SST, and the source then frees those files normally.
  • Fork checkpoints have no expiry. A fork compaction that falls behind keeps the source's files alive and costs storage, but never loses data.
  • Block reads for external SSTs use the owner's path: /v1/databases/<owner>/ssts/…. A fork's reads therefore hit the cache entries the source already warmed.

Optional sharding package

ShardRouter.put(group, key, value)
  map = cached ShardDirectory(group).rangeMap   # { version, ranges → DatabaseId }
  db  = map.databaseFor(key)
  DbClient.put(db, key, value)
    DatabaseSealedError { successors } → refresh map, retry once
    KeyOutOfRangeError                 → refresh map, retry once

ShardSplit.split(group, db, atKey k)          # seal first, fork once
  DatabaseLifecycle.seal(db, [a, b])          # memtable flushed, fenced
  cp = checkpoint of the sealed manifest
  a  = forkRange(db, cp, [lo, k), newId)
  b  = forkRange(db, cp, [k, hi), newId)
  ShardDirectory(group).publish(version + 1, a, b)
  # writes to db fail during the split; the router retries
  # against a and b once the new map is published
  • Range shards, not hash shards. Range and prefix scans stay in one database. Hash sharding (HashRing) would make every scan a scatter-gather merge.
  • Seal-then-fork is the simple version: writes pause for one memtable flush plus a few manifest CAS operations. Forking before sealing shortens the pause, but needs a second catch-up fork for rows flushed in between.
  • Why the core needs no map versions: a stale router can only hit a sealed or out-of-range database, and both fail with typed errors that tell it to refresh.
  • What callers give up: atomic batches and transactions across databases. A single hot key still can't exceed one Durable Object.
